Hierarchical data formats

A flat table repeats a set of columns across rows. Hierarchical data can nest objects and lists. JSON, XML, YAML, and TOML describe structured data using different syntax; choosing a format does not determine when an application validates its schema.

  • JSON: Objects contain string keys and values; arrays contain ordered values. Values can be objects, arrays, strings, numbers, booleans, or null. Use double quotes and omit comments and trailing commas. See the JSON specification.
  • XML: Elements use tags and can carry attributes or nested elements. An application or schema gives their text values meaning and can validate structure. See the XML specification.
  • YAML: Indentation expresses nesting, mappings hold key/value pairs, and sequences hold ordered items. It is common in configuration. Use a safe loader for untrusted YAML. See the YAML specification.
  • TOML: Key/value pairs, tables such as [project], and arrays describe configuration. Indentation does not define its hierarchy. TOML has no null value. See the TOML specification.
{
  "student": {
    "name": "Alice",
    "courses": ["DS2022", "CS3240"],
    "address": {"city": "Charlottesville"}
  }
}

In Python, data["student"]["courses"][0] returns "DS2022". Objects become dictionaries and arrays become lists. "21" is a string; 21 is a number. Parsing valid JSON checks syntax, while application validation checks requirements such as a required name or an allowed age.

NoSQL data models

NoSQL is an umbrella term, often expanded as “not only SQL.” It includes several data models; it does not promise a particular scaling strategy, transaction guarantee, or absence of schemas.

  • Key-value: Retrieve a value using its key, such as a shopping cart by session ID. Redis and DynamoDB are examples, with capabilities beyond this simple model.
  • Document: Store and query structured records with nested fields and arrays. MongoDB is an example.
  • Wide-column: Organize distributed data around partition keys and related rows. In the sensor example, (sensor_id, day) selects a partition and timestamp orders rows inside it. Cassandra CQL tables declare typed columns; “wide-column” does not mean every engine accepts arbitrary fields. See Cassandra data definitions.
  • Graph: Nodes represent entities and edges represent relationships. A path follows multiple edges, such as a reader connected to an author through a book. Nodes and vertices mean the same thing. See property graph concepts.

A wide-column database differs from an analytical columnar database. Columnar storage groups values from a column for operations such as scanning and aggregation. Row-oriented storage groups a row’s values. These are workload and storage choices, not universal promises about which database will be fastest.

Specialized data and queries

Time-series systems focus on time-stamped measurements, time windows, and aggregations. Ledger systems preserve a history of changes; some add cryptographic evidence that makes tampering detectable. An order’s latest status can be derived from events such as Created, Processing, and Shipped.

Vector search finds embeddings near a query vector according to a chosen similarity measure. Embeddings encode learned features; nearby results are candidates, not proof that statements are true. The slide’s two-dimensional points illustrate proximity, while practical embeddings commonly have many more dimensions. See MongoDB’s vector search overview.

MongoDB documents and identifiers

A MongoDB database contains collections, and a collection contains documents. Documents use BSON, which supports additional types beyond JSON, including dates, binary values, and ObjectId. Fields can contain nested documents and arrays. Collections can allow varying fields while still applying declared validation rules. See BSON types and schema validation.

In a standard collection, _id uniquely identifies a document. Clients commonly generate an ObjectId when it is omitted. ObjectId contains 12 bytes and is often displayed as 24 hexadecimal characters; an _id can also use another supported type. Our examples deliberately use readable strings such as "book_001". See the _id field.

The bookstore: embed or reference?

An author can have a small biography embedded inside the author document. Books may have several authors, so each book can hold an array of author IDs. Reviews can grow without a fixed bound, making a separate reviews collection with a book reference a useful design.

{
  "_id": "author_001",
  "name": "Jane Austen",
  "bio": {"short": "English novelist", "country": "England"}
}

{
  "_id": "book_001",
  "title": "Pride and Prejudice",
  "author_ids": ["author_001"]
}

Embedding can keep small, bounded data that is owned and read together in one document. Referencing can keep shared or independently changing facts in one place. A reference ID is not an automatically enforced foreign key: the application must decide how to maintain and resolve it. Reads can use additional queries or aggregation such as $lookup. See MongoDB’s embedding and reference guidance.

The modeling activity explores another boundary: copying an author into several books versus sharing one referenced author. Change a biography and inspect how many copies require updates. Discuss whether reviews are bounded, whether author information is shared, and which fields an application normally reads together.

Use the connection URI supplied by your class deployment. These Bash/Zsh commands read it without saving it in shell history or displaying it as you type:

printf 'MongoDB connection URI: '
IFS= read -r -s MONGODB_URI
printf '\n'

The script connects using the environment value and writes only to ds2022_lecture06. URI credentials containing reserved characters must use the appropriate percent encoding. Keep credentials out of code and Git. See connection strings and mongosh scripts.

Start an interactive session with mongosh --nodb, then connect using the same environment value and try these operations one at a time. The insert and delete use a dedicated practice review ID:

db = connect(process.env.MONGODB_URI)
use ds2022_lecture06
db.books.find({author_ids: "author_001"})

db.reviews.insertOne({
  _id: "review_practice", book_id: "book_001",
  user: "Sam", rating: 4
})

db.reviews.updateOne(
  {_id: "review_practice"},
  {$set: {rating: 5}}
)
db.reviews.find({_id: "review_practice"})
db.reviews.deleteOne({_id: "review_practice"})

A filter chooses matching documents. $set changes specified fields while keeping the others. The returned counts help distinguish a matched document from a changed document. MongoDB normally acknowledges each operation without a separate SQL-style commit; multi-document transactions use an explicit session. See MongoDB CRUD.

Transactions and replicated data

ACID describes transaction properties: atomicity groups changes, consistency preserves declared rules, isolation defines permitted concurrent observations, and durability preserves committed results under the system’s guarantees. These properties are not exclusive to relational databases. MongoDB supports atomic single-document updates and multi-document transactions. See MongoDB transactions.

BASE is a loose design description: Basically Available, Soft state, Eventually consistent. It is not a certification that ensures speed or uptime. Eventual consistency guarantees convergence once updates stop and communication and delivery continue. The consistency in ACID’s name concerns valid state, while replica consistency concerns what different reads can observe. See Werner Vogels’ explanation of eventual consistency.

The replication activity starts with two copies. Write a new store-hours value at A, compare it with B, then deliver the update. Explore more adds disconnected links, another replica, and explicit reads. This model illustrates lag; actual MongoDB guarantees depend on topology, failure handling, and read/write settings. See secondary reads.

WORM and retained history

Write Once, Read Many storage can prevent changing or deleting protected object versions during a configured retention period or legal hold. Retention may expire, and the exact rules depend on the system. WORM alone does not provide cryptographic verification; a ledger may add a verifiable history. See S3 Object Lock.
